# 작업 정리 — 2026-07-27

점주 웹을 API 경유 BFF로 분리하고, 그 과정에서 발견한 컨테이너 노출 문제와 검증 우회 구멍을 정리했다.

## 1. 시작점 — 컨테이너 안에 인프라 설정이 다 보였다

`docker exec` 로 들어가면 `/app` 에 `Dockerfile`, `docker-compose.yml`, `docker/`, `global-bundle.pem` 이 그대로 있었다.

원인은 `.dockerignore` 가 아니라 `docker-compose.yml` 의 `.:/app` 바인드 마운트였다. 이 마운트는 이미지의 `/app` 을 호스트 폴더로 통째로 덮어쓰기 때문에, 빌드 시점 설정이 런타임에는 아무 의미가 없다. 파일 읽기나 RCE 취약점 하나로 인프라 구성과 시크릿이 함께 넘어가는 상태였다.

### 조치

- `docker-compose.yml` 에서 바인드 마운트 제거. 코드는 이미지에 구운 것만 사용한다.
- `Dockerfile` 에서 `COPY . .` 제거 → `manage.py`, `config/`, `apps/` 만 명시적으로 복사.
- entrypoint 를 `/usr/local/bin/` 으로 이동. `requirements.txt` 는 `/tmp` 에서 설치 후 삭제.
- `.dockerignore` 를 allowlist 방식으로 전환 (`*` 로 전부 막고 `!` 로 재허용).
- 마운트 제거로 사라진 것들 보강: `media_data` 볼륨 추가, `env_file: .env` 주입(설정 누락 방지), RDS CA 번들 `:ro` 마운트.
- `no-new-privileges:true` 적용, `ADMIN_BIND` 기본값을 `127.0.0.1` 로 (설정을 깜빡해도 관리자 웹이 외부에 안 열리도록).

## 2. 점주 웹 3-tier 분리

`web_bff/` — 점주 웹 전용 Django 프로젝트를 새로 만들고 8개 화면을 전부 옮겼다.

핵심은 `settings.py` 의 `DATABASES = {}`. DB 커넥션 자체가 없고, 모델을 가진 앱도 `django.contrib.auth` 도 `INSTALLED_APPS` 에 없다. 실수로 ORM 을 호출하면 그 자리에서 터진다.

| 항목 | 내용 |
|---|---|
| 인증 | `/api/v1/auth/login` 의 JWT 를 Redis 세션에 보관. `ApiSessionMiddleware` 가 `request.web_user` 세팅, `@owner_required` 가 role 확인 |
| 이미지 | `docker/Dockerfile.web` + `requirements-web.txt` (Django·httpx·redis 뿐, **mysqlclient 없음**) |
| 진입점 | `manage_web.py` |
| 파일 다운로드 | `ApiClient.raw()` 로 중계. 브라우저에 JWT 가 없어 API URL 을 직접 열 수 없다 |
| 파일 업로드 | 본문 JSON + 별도 multipart 엔드포인트 2단계 |

이관한 화면: 대시보드 · 주문 관리 · 상품 · 카테고리 · 매출 분석 · 리뷰 관리 · 마이페이지 · 내 매장 관리 · 점주 회원가입.

`apps/web` 과 `config/urls_web.py` 는 제거했고, `web` 서비스가 8001 포트에서 새 이미지로 뜬다.

## 3. 이관하며 서버로 옮긴 검증 규칙

가장 값어치 있는 부분. 아래는 전부 `apps/web` **화면에만** 있던 검사라, API 를 직접 호출하면 그냥 통과했다.

| 규칙 | 옮긴 곳 |
|---|---|
| 심사 대기·반려 매장에 상품/카테고리/휴무일/공지 등록 금지 | `_assert_reviewable`, `store._guard` |
| 상품 가격 상한 1천만원 | `ProductSerializer.validate_price` |
| 카테고리 이름 중복 | `CategorySerializer.validate` |
| 이메일 형식·중복 | `OwnerProfileSerializer.validate_email` |
| 비밀번호 최소 길이 (화면 8자 / API 4자로 서로 달랐음) | 8자로 통일 |
| 주문 상태 전이 규칙 (화면에서 직접 검사 → 아무 상태로나 변경 가능했음) | `/owner/orders/<pk>/accept` 등 서버 판단 |
| 주민번호 형식·중복, 사업자등록증 검증, 승인 전 로그인 차단 | `store_signup` |

### 함께 잡은 버그

`sales_summary` 가 `_SALES_STATUSES` 를 선언만 하고 쓰지 않아 **취소·거절 주문까지 매출에 합산**되고 있었다. 웹 화면은 자체적으로 걸러냈기 때문에 같은 지표가 화면과 API 에서 서로 달랐다. 필터를 적용하고 `sales_by_menu` 에도 같은 조건(기간·매장·상태)을 맞췄다.

## 4. 신규 API

`owner/restaurants`(GET·POST) · `owner/restaurants/<pk>`(상세 통합) · `.../edit-request` · `.../image` · `.../closed-dates` · `.../regular-closed-days` · `.../notices` · `owner/closed-dates/<pk>` · `owner/notices/<pk>` · `owner/withdrawal` · `owner/reviews/<pk>/delete` · `owner/categories/<pk>/move` · `owner/signup/store`

설계상 눈여겨볼 것:

- **매장 상세는 한 번의 호출로 묶었다.** 화면 하나에 매장·휴무일·정기휴무·공지·수정요청·심사상태가 다 필요한데 따로 부르면 6회 왕복이 된다.
- **카테고리 순서 변경**은 `select_for_update` + 트랜잭션. 웹에서 `display_order` 를 두 번 PUT 하면 중간에 끊길 때 순서가 깨진다.
- **점주 리뷰 삭제**는 고객용 하드 삭제와 분리. 사유가 남는 소프트 삭제라 별도 경로가 필요했다.
- **탈퇴 신청**도 `DELETE /owner/profile`(즉시 비활성화)과 분리. 웹의 탈퇴는 관리자 승인을 거치는 요청 접수다.

## 5. 부수적으로 정리한 것

- **`.gitattributes` 추가** — Windows 도구가 트리 전체를 CRLF 로 바꿔 434개 파일이 통째로 변경된 것처럼 잡히던 문제. `docker/entrypoint.sh` 가 CRLF 면 컨테이너가 `bad interpreter` 로 죽는다.
- **미추적 배포 파일 커밋** — `docker-compose.prod.yml`, `scripts/deploy_remote.sh`, `.github/workflows/ci-cd.yml`, `docs/DEPLOYMENT.md`, `.env.example` 이 오랫동안 untracked 였다. `git clean` 한 번이면 배포 파이프라인이 통째로 사라질 상태였다.
- **CI 배포 job 게이트** — 시크릿 미설정으로 매 푸시마다 실패하던 것을 `vars.DEPLOY_ENABLED == 'true'` 로 감쌌다. 이제 실패가 아니라 skipped 로 지나간다.
- **`is_reviewable_restaurant` 공용화** — `restaurants/selectors.py` 로 이동.
- **HTTPS 프록시 대응** — `CSRF_TRUSTED_ORIGINS` 는 스킴까지 정확히 맞아야 한다. `USE_X_FORWARDED_PROTO` 옵션 추가(프록시가 헤더를 붙일 때만 켜는 것을 전제).

## 6. 남은 과제

1. **CI 워크플로가 이미지를 하나만 빌드한다.** 이제 `hackmin`(api·admin-web)과 `hackmin-web` 둘이 필요하다. 배포 재개 전 `docker/Dockerfile.web` 빌드·푸시 단계 추가와 `HACKMIN_WEB_IMAGE` 설정이 필요하다.
2. **`apps/admin_web` 은 아직 ORM 직결.** 같은 방식으로 옮기려면 신규 API 4~5개(탈퇴 승인, 매장 수정 요청 승인 등)가 더 필요하다. 현재 구조에서 가장 큰 노출면이다.
3. **`DJANGO_DEBUG=1` 로 운영 중.** 개발 중이라 의도한 것이지만, 예외 하나로 소스와 환경변수가 노출된다.
4. **DB 계정 분리 미적용.** `api` 와 `admin-web` 이 같은 계정으로 RDS 에 붙는다. 서비스별로 권한을 나누면 컨테이너 하나가 뚫려도 피해 범위가 준다.
5. **`_to_delete/` 정리** — 제거한 `apps/web` 사본과 stale git lock 파일이 들어 있다. 확인 후 삭제.
